# Rust 移行計画

作成日: 2026-11-16 / 対象: `fcs` (Python 版, `main` = `4307edb`)

この文書は着手前に書いた計画である。実施状況と結果は 8 章にある。

## 1. 決定済みの方針

| 項目 | 決定 |
| --- | --- |
| 目的 | 計算速度の向上と、Python なしで動く単一バイナリでの配布 |
| リポジトリ | Rust 版は新しいリポジトリに作る。この Python リポジトリはそのまま残す |
| 描画 | Python に残す。Rust 版は弾道データをファイルに出力し、Python 側のスクリプトが描く |
| 一致度 | 命中するケースで、方位角・仰角・到達時間が Python 版と表示桁 (小数 2 桁) で一致する |
| 発射角の探索 | Powell 法を使う。現行の L-BFGS-B は要件ではない。Python 版も移行の最初に Powell 法へ切り替える |

この決定から、次のことが決まる。

- Python 版は「参照実装」と「描画」の役割で残る。Rust 版のテストの正解データは Python 版から作る。
- 弾道 (ODE) も探索 (Powell 法) も、SciPy と同じアルゴリズムを自前で実装する。両方の版が同じ手順で動くので、最終結果だけでなく途中経過も照合できる。
- 届かない目標 (`out_of_range` / `out_of_time`) の出力値の一致は要件ではない。ただし同じアルゴリズムなので一致するはずで、食い違いは不具合の手がかりとして調べる。

### 2.1 Powell 法の試行結果 (2026-11-16)

Python 版の `minimize` を差し替えて試した。リポジトリのコードは変更していない。目標は 161 件 (README の例 1、近距離 60、頭上 40、地上 40、届かない目標 20)。

**SciPy の既定のままでは使えない。** `method="Powell"` に現行の `bounds` を渡しただけだと、README の例を含めて命中の大半を逃した (L-BFGS-B で命中する 138 件のうち 81 件を逃す)。原因の切り分けはしていないが、候補は 2 つある。初期の探索方向の長さが 1 rad で、解 (初期値から数度以内) に対して大きすぎること。`bounds` を付けると仰角の一次元探索が `[0, π]` 全体を対象にし、別の谷へ飛ぶこと。

**次の設定にすると、L-BFGS-B と同じ解に収束した。**

- `bounds` を渡さない。目的関数の中で仰角を `[0, π]` に切り詰める。
- 初期の探索方向を 0.02 rad に縮める (`direc = 0.02 * I`)。
- `xtol = ftol = 1e-6`、関数評価の上限は 300 回のまま。

| ケース | 命中 (L-BFGS-B → Powell) | 弾道の数、中央値 (最大) | Python 版の計算時間、中央値 |
| --- | --- | --- | --- |
| README の例 | 命中 → 命中 | 25 → 103 | 37 → 144 ms |
| 近距離 (60 件) | 57 → 57 | 37 (115) → 147 (192) | 54 → 207 ms |
| 頭上 (40 件) | 40 → 40 | 56 (112) → 130 (255) | 79 → 172 ms |
| 地上 z = 0 (40 件) | 40 → 40 | 88 (169) → 208 (301) | 84 → 154 ms |
| 届かない目標 (20 件) | 0 → 0 | 314 (370) → 201 (237) | 398 → 248 ms |

- 命中した 138 件は全て同じ解で、差は角度で最大 0.0003°、到達時間で最大 0.0005 ms。
- 命中時の最接近距離は、ほぼ全件で表示上 0。最大は地上の目標の 2.5e-3 m で、これは評価回数が上限に達したケース。
- **命中するケースの評価回数は 3〜4 倍に増える。** 届かない目標では逆に 3 分の 2 に減る。Python 版は切り替え後、命中するケースで 3〜4 倍遅くなる。
- 初期幅 0.1 rad でも結果は同等だった。許容誤差を 1e-9 にすると評価回数が増え、地上の 1 件が上限に達して命中を逃した。

設定値 (初期幅、許容誤差、上限回数) の最終決定はフェーズ 0 で行う。

## 3. 移行後の構成

### リポジトリ

新しいリポジトリ `fcs-rs` に、ライブラリと `lead` コマンドを 1 つの package として置く。

```
fcs-rs/
  Cargo.toml
  src/
    lib.rs          公開 API
    types.rs        Projectile, Target, Atmosphere, Solution, Status など
    ode.rs          RK45 (Dormand–Prince) とイベント検出。弾道に依存しない汎用部品
    trajectory.rs   状態方程式、着地イベント、弾道の計算   <- solver.py, terminal_events.py
    closest.rs      二次近似と四次関数の最小点            <- approximate_decision.py, quartic_minimum.py
    powell.rs       Powell 法と一次元探索 (Brent 法)。弾道に依存しない汎用部品
    optimizer.rs    発射角の探索                          <- optimizer.py
    validate.rs     入力値の検査                          <- main.py の _find_invalid_inputs
    main.rs         CLI (lead)                            <- main.py
  tests/
    fixtures/       Python 版から出力した正解データ (JSON)
    *.rs            層ごとの照合テスト、CLI のテスト
```

### Python 版との対応で変える点

移植であって作り直しではないので、アルゴリズムは変えない。変えるのは次の点だけ。

- **入力値の検査をライブラリ側に置く。** Python 版は CLI でしか検査していない。Rust 版は公開 API が `Result` を返し、CLI はそれを終了コード 2 に変換する。
- **角度の順序の取り違えを型で防ぐ。** Python 版は `(phi, theta)` と `(theta, phi)` が混在している。Rust 版は名前付きフィールドの構造体だけを使う。
- **`t_dir` を `velocity` と呼ぶ。** 中身は目標の速度ベクトルである。CLI の引数名 (`direction_x` など) は互換のため変えない。
- **`--plot` は持たない。** 代わりに `--dump <path>` で弾道データを JSON に出力する (5 章 フェーズ 5)。

## 4. 設計

### 4.1 各部品の実装方針

| 部品 | 方針 | 理由 |
| --- | --- | --- |
| RK45 とイベント検出 | **自前実装**。SciPy の `RK45` と `solve_ivp` のイベント処理をそのまま移植する | 二次近似は積分のステップ点そのものを使うので、ステップの刻み方まで同じにしないと層ごとの照合ができない。状態は 6 次元固定で、実装は 300 行程度に収まる |
| 二次式の当てはめ | 自前実装。最大 5 点・3 係数の最小二乗 | 外部 crate を入れるほどの規模ではない |
| 四次関数の最小点 | 自前実装。導関数 (三次式) を解析的に解く | `np.roots` (固有値計算) の代わり。根の実部を全て候補にする規則は Python 版と同じにする |
| Powell 法 | **自前実装**。SciPy の `_minimize_powell` と、その中の一次元探索 (区間の囲い込みと Brent 法) を移植する | 微分を使わないので数値微分が要らず、実装は 200 行程度。外部 crate に頼らずに済み、Python 版と評価点の列まで照合できる |
| CLI | `clap` (derive) | 終了コード 2 が argparse と同じ |
| JSON | `serde`, `serde_json` | `--dump` とテストの正解データ |

依存 crate は `clap`, `serde`, `serde_json` の 3 個に抑える。数値計算は全て自前で、C コンパイラも要らない。配布物が小さくなり、ビルドも速い。

### 4.2 SciPy から移植する挙動

以下は記憶に基づく一覧なので、実装時に SciPy 1.17.0 のソース (`scipy/integrate/_ivp/rk.py`, `ivp.py`, `common.py`, `scipy/optimize/_optimize.py`) と突き合わせること。

**RK45 (`solve_ivp` の既定)**

- Dormand–Prince 5(4) の係数。許容誤差は `rtol = 1e-8`, `atol = 1e-6` (`atol` は SciPy の既定値で、Python 版は指定していない)。
- 最初の刻み幅は `select_initial_step` の手順で決める。
- 刻み幅の制御: 誤差ノルムは `atol + max(|y|, |y_new|) * rtol` で割った値の二乗平均平方根。倍率は `0.9 * err^(-1/5)` を `[0.2, 10]` に制限し、棄却直後の採用では 1 を超えない。
- 最後の一歩は `span_end` を越えないように縮める。
- 出力点は採用したステップの終点そのもの (`t_eval` なし)。

**イベント (着地)**

- 各ステップの終点でイベント関数を評価し、正から負への符号変化だけを拾う。
- 発生時刻は、密出力 (ステップ内の四次補間) に対して Brent 法で求める。
- 終了イベントなので、最後の出力点は「イベント時刻と、その時刻の密出力の値」に置き換わる。
- `FallEvent` は `t <= 0` で 1.0 を返す。発射点 (z = 0) を着地とみなさないための仕掛けで、そのまま移植する。

**Powell 法 (`minimize(method="Powell")`, `bounds` なし)**

- 目的関数は最接近距離の 2 乗。変数は `(phi, theta)`。仰角は目的関数の中で `[0, π]` に切り詰める (2.1 節)。
- 初期の探索方向は座標軸で、長さは設定値 (試行では 0.02 rad)。
- 外側の反復 1 回で、全ての方向について順に一次元探索をする。その後、反復の始点から終点への変位を新しい方向の候補とし、Numerical Recipes と同じ判定で、最も改善が大きかった方向と入れ替える。
- 一次元探索は、黄金比で広げながら最小点を挟む 3 点を見つけ (`bracket`)、Brent 法 (放物線補間と黄金分割) で詰める。許容誤差は `xtol` の 100 倍。
- 終了条件は、反復 1 回での改善が `ftol` (相対) 以下になるか、関数評価が上限に達すること。上限は反復の区切りでしか確認されないので、少し超えることがある。
- 探索後の処理 (仰角が π/2 を超えたら折り返す、方位角を `(-π, π]` に畳み込む、最接近距離と `tolerance` で `status` を決める) は現行の Python 版と同じ。

### 4.3 合格基準

「命中時に表示桁で一致」を、次のように数値で定義する。

| 対象 | 基準 |
| --- | --- |
| 弾道 (層 1) | ステップ数が同じで、時刻と位置の相対誤差が 1e-9 以下 |
| 最接近点 (層 2) | 時刻と距離の差が 1e-7 以下 |
| 探索結果、命中するケース | 方位角・仰角の差が 0.005° 以下、到達時間の差が 0.005 ms 以下、`status` が一致 |
| 探索結果、命中しないケース | 命中か否かは全件一致。`out_of_range` と `out_of_time` の区別は一致を目標とし、食い違ったものは原因を確認して記録する |
| 探索の経過 | 関数評価の回数が Python 版と一致することを目標とする。合否の基準にはしないが、ずれたケースは原因を確認する |
| CLI | README に載せている実行例は、計算時間の列を除いて文字列が完全に一致。終了コードと stderr のメッセージも一致 |

全ケースで文字列の完全一致を求めないのは、同じアルゴリズムでも三角関数などの最後の 1 ビットの違いが探索の中で増幅され得るからである。差が小さくても、小数 2 桁の丸めの境目をまたぐケースは残る。別のアルゴリズム同士 (L-BFGS-B と Powell 法) でも差は 0.0003° 以内だったので (2.1 節)、0.005° は余裕のある基準である。

### 4.4 性能要件

**要件は「Python 版より速いこと」だけで、具体的な時間の目標は置かない。**

比べる相手は、Powell 法に切り替えた後の Python 版である。同じ PC、同じ入力で、次の 2 つがどちらも Python 版より短ければ合格とする。

- 計算時間 (`calc_msec`)。2 章の 4 種類のケース (README の例、近距離、頭上、届かない目標) のそれぞれで比べる。
- コマンドの起動から終了までの時間。README の例で比べる。

参考として、Python 版の値は次のとおり。

| 指標 | Python 版 (現行) | Python 版 (Powell 法) |
| --- | --- | --- |
| README の例の計算時間 | 37 ms | 約 160 ms (切り替え後に実測) |
| 届かない目標の計算時間 | 約 400 ms | 約 250 ms |
| コマンドの起動から終了まで | 約 825 ms | 約 1000 ms (切り替え後に実測) |

弾道 1 本が Python で 1.24 ms かかっているのは、状態方程式を 1 回呼ぶごとのインタプリタのコストが大半なので、同じアルゴリズムをそのまま移植するだけで要件は満たせる見込みである。現行の L-BFGS-B 版と比べても速くなるはずだが、これは要件ではなく、実測して記録するだけにする。評価回数を減らす工夫など、要件を超える高速化は移植が合格してから別の作業として扱う。

## 5. 進め方

下の層から順に作り、各層を Python 版の正解データと照合してから次へ進む。規模は相対的な目安。

### フェーズ 0: 準備 (小)

Python リポジトリ側:

- **探索を Powell 法に切り替える。** `optimizer.py` の `minimize` を 2.1 節の設定に変える。設定値 (初期幅 0.02 か 0.1 か、許容誤差、上限回数) は、2.1 節より広い目標の集合で実測して決める。確認するのは、命中の取りこぼしがないこと、上限に達する命中ケースの数、評価回数の分布。README の実行例の出力が変わらないことを確かめ、`CLAUDE.md` の記述を更新する。
- 切り替え後の基準値 (2 章の表) を取り直す。
- 正解データを出力するスクリプト `fcs/scripts/dump_fixtures.py` を追加する。出力は JSON で、Python 版のコミットと scipy / numpy の版を記録する。内容は次の 3 種類。
  - 層 1: 発射条件ごとの弾道 (`t`, 弾の位置, 目標の位置)。両方の `drag_type`、着地で終わるもの、`span_end` で打ち切られるもの、仰角 0 と 90° を含める。
  - 層 2: 同じ弾道に対する `find_closest_point` の結果。サンプルが 3 点未満の場合を含める。
  - 層 3: 目標ごとの `run_optimization` の結果と、関数評価の回数。README の例、近距離、頭上、地上 (z = 0)、届かない目標を含める。数件については、評価した `(phi, theta)` と目的関数の値の列も出力する。

Rust リポジトリ側:

- リポジトリを作り、`cargo init`、ライセンス (Python 版と同じ)、`rustfmt` / `clippy` / `cargo test` を回す CI を用意する。

完了条件: Python 版が Powell 法で動き、その正解データが Rust リポジトリの `tests/fixtures/` にあり、空のテストが CI で通る。

### フェーズ 1: 型と弾道 (大)

- `types.rs`, `ode.rs`, `trajectory.rs` を実装する。
- `ode.rs` は、解析解のある問題 (等加速度運動、指数減衰) での単体テストも持つ。

完了条件: 層 1 の正解データと 4.3 の基準で一致する。

### フェーズ 2: 最接近点 (中)

- `closest.rs` を実装する。二次式の当てはめ、四次関数の係数の組み立て、区間に制限した最小点、3 点未満の場合の処理。
- 当てはめは時刻を平均でずらしてから解く (条件数を下げるため)。結果は Python 版と同じ係数に戻す。

完了条件: 層 2 の正解データと一致する。四次関数の最小点は、重根や区間の端が最小になる場合の単体テストを持つ。

### フェーズ 3: 発射角の探索 (中)

- `powell.rs` を実装する。解の分かっている関数 (二次形式、Rosenbrock 関数) での単体テストを持ち、SciPy の同じ設定での評価回数と比べる。
- `optimizer.rs` と `validate.rs` を実装し、公開 API (`solve_lead` のような 1 つの関数) を確定する。

完了条件: 層 3 の正解データと一致する。評価点の列を出力した数件で、探索の経過が Python 版と一致する。

### フェーズ 4: CLI (小)

- 位置引数 10 個とオプション (`--span-end`, `--tolerance`, `--std-density`, `--std-temp`, `--lapse-rate`, `--lapse-index`, `--drag-type`, `--readable`/`-r`) を Python 版と同じ名前と既定値で用意する。
- 出力形式、終了コード (0 / 2 / 3 / 4)、stderr の `lead: <status>: <message>` を同じにする。
- argparse との違いを潰す。分かっているものは次のとおり。
  - `-10` のような負の数を位置引数として受け取る (clap は既定ではオプションと解釈する)。
  - `nan` と `inf` は数値として解釈した上で、検査で弾いて終了コード 2 にする。
  - 複数の検査エラーは `; ` でつないで 1 行にする。

完了条件: README の実行例と、不正な入力の例について、stdout・stderr・終了コードのテストが通る。

### フェーズ 5: 描画との連携 (小)

- Rust 版に `--dump <path>` を追加する。内容は、最適な発射角での弾道 (`t`, 弾の位置, 目標の位置) と最接近点。
- Python リポジトリに、このファイルを読んで `plot_3d` を呼ぶスクリプトを追加する。

### 設定値を決めた実測 (フェーズ 0)

目標 280 件 (標準の弾で近距離 100・頭上 40・地上 40・届かない目標 20、高速の弾 40、低速で摩擦抵抗の弾 40) で、初期幅 0.02 / 0.1 rad と上限 300 / 600 回の 4 通りを L-BFGS-B と比べた。

- 4 通りとも、L-BFGS-B で命中する 248 件を全て同じ解で命中させた (角度差は最大 0.0001°)。取りこぼしも、新たに命中するものもなかった。
- 初期幅 0.02 と 0.1 に優劣はなかった。評価回数の中央値はどちらも 125〜215 回。
- 上限を 600 回にすると、地上の目標で最大 391 回まで使うケースがあった。300 回で打ち切っても、そのケースの最接近距離は 2e-5 m で命中のままだったので、上限は 300 回に据え置いた。

| 比較対象 | 件数 | 結果 |
| --- | --- | --- |

4.3 の合格基準は全て満たした。基準にしていない項目で、次の 2 つが一致しなかった。

- 探索で計算する弾道の数が 282 件中 274 件で違う (平均 10 %、増減どちらもある。合計では 0.7 %)。Python 版は二次式の当てはめと三次方程式の根に LAPACK (`np.polyfit`, `np.roots`) を使い、Rust 版は閉じた式で解く。命中付近では最接近距離が丸め誤差 (約 1e-6 m) の大きさになり、一次元探索がその誤差に左右される。Python 側の 2 か所を同じ閉じた式に置き換えると、282 件全てで結果も回数もビット単位で一致する。
- `out_of_range` と `out_of_time` の区別が 1 件で違う。最良の弾道がちょうど `span_end` で着地するケース。

### 配布

fcs-rs の `.github/workflows/release.yml` が、`v<版>` のタグを push するとリリースを作る。
タグと `Cargo.toml` の版が合わないと失敗する。

| 対象 | 形式 | 単体で動かすための設定 |
| --- | --- | --- |
| `x86_64-pc-windows-msvc` | zip | C ランタイムを静的リンク (`+crt-static`) |
| `x86_64-unknown-linux-musl` | tar.gz | musl の静的バイナリ。glibc の版に依存しない |
| `aarch64-apple-darwin` | tar.gz | なし |

各ビルドは、README の最初の例の出力 (計算時間の列を除く) が `46.95 36.46 0.00 601.31` になることを確かめてから、アーカイブにする。
`cargo test` はこの CI では動かさない。正解データは Windows で作ったもので、Linux と macOS では数学関数ライブラリの違いから、弾道のビット単位の一致を求めるテストが通らない可能性がある。

完了条件の確認 (2026-11-18): リリース `v0.1.0` から Windows 版をダウンロードし、PATH を `C:\Windows\System32` だけにして実行した。

- README の 2 つの例は同じ値を出力し、終了コードは 0。
- 遠い目標は `out_of_time` で終了コード 4、不正な引数は終了コード 2 で、どちらも手元でビルドしたものと同じ。
- exe は `VCRUNTIME140` を参照していない。

この PC には Rust と Python が入っており、PATH から外しただけなので、厳密に「どちらも入っていない環境」での確認ではない。
Linux 版と macOS 版は CI 上の出力確認だけで、ダウンロードしての確認はしていない。
